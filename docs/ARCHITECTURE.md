# Architecture

This document describes the architectural decisions, trade-offs, and operational characteristics of the Support Ticket Classifier.

---

## 1. Component Overview

| Component             | Responsibility                                          | Technology                |
|-----------------------|---------------------------------------------------------|---------------------------|
| **API Gateway**       | TLS termination, rate limiting, request routing         | Nginx Ingress + cert-manager |
| **API Service**       | Authentication, validation, inference orchestration     | FastAPI + Uvicorn + Gunicorn |
| **ML Inference**      | TF-IDF vectorization + Logistic Regression prediction   | scikit-learn (in-process) |
| **Cache**             | Repeated-prediction cache, JWT denylist                 | Azure Cache for Redis     |
| **Primary Store**     | Tickets, predictions, feedback, users                   | Azure Database for MySQL  |
| **Object Store**      | Versioned model artifacts                               | Azure Blob Storage        |
| **Secrets**           | JWT secret, DB password, ACR pull secret                | Azure Key Vault           |
| **Observability**     | Logs, metrics, traces, alerts                           | Application Insights + Log Analytics + Prometheus + Grafana |
| **CI / CD**           | Lint → test → build → push → deploy                     | GitHub Actions            |

## 2. Request Flow (single prediction)

```
[Client]
   │  HTTPS POST /predict
   ▼
[Azure API Management]               ← API key + per-key rate limit
   │
   ▼
[Nginx Ingress Controller]           ← TLS, host routing, basic rate limit
   │
   ▼
[FastAPI Pod (Uvicorn worker)]
   │
   ├─ middleware: request timing, request ID
   ├─ dependency: get_current_user → decode JWT (in-mem secret cached)
   ├─ dependency: get_predictor → singleton model on app.state
   │
   ├─ utils.helpers.text_hash(subject + body)
   ├─ Redis GET cache:{hash}
   │     hit  → return cached result (latency ≈ 4 ms)
   │     miss → continue
   │
   ├─ preprocessing.preprocess(text)
   ├─ pipeline.predict_proba([clean_text])
   ├─ build top-3, decide routing queue
   │
   ├─ Redis SETEX cache:{hash} 3600 {result}
   ├─ MySQL INSERT INTO predictions (...)         ← async, fire-and-forget
   ├─ logger.info("prediction.served")            ← JSON log to stdout
   ▼
[Response JSON to client]
```

Typical end-to-end latency (warm pod, cache miss): **18 ms p50, 95 ms p99**.
With cache hit: **~5 ms p50**.

## 3. Why these choices

### Why FastAPI?
- Async support gives non-blocking I/O for downstream Redis/DB calls.
- Pydantic v2 validation eliminates a layer of manual schema code.
- OpenAPI is autogenerated — kills documentation drift.

### Why Logistic Regression over a transformer?
- F1-macro 0.942 vs 0.954 for Sentence-BERT — small quality gap.
- LR inference is **10x faster** and the model is **100x smaller**.
- We can serve LR on CPU; transformers need GPU node-pools (3-4x cost).
- LR is interpretable: support agents can ask "why did it predict Billing?" and we can show the top contributing n-grams (`coef_` on TF-IDF).

The transformer variant is still available behind a feature flag for low-confidence Finance tickets, where mistakes are most expensive.

### Why MySQL (not Postgres)?
- Existing org-wide standard — DBA tooling, backups, monitoring already in place.
- No feature in this workload (JSONB, full-text search) needs Postgres.

### Why Redis cache?
- 28% of tickets are near-duplicates (canned product issues, status-page outages). Caching these avoids re-running inference.
- Cache hit rate observed in production: **22-30%** depending on hour-of-day.

## 4. Scalability

- **Horizontal**: 3 pods baseline, scales to 15 via HPA on CPU + memory. Stateless containers — no sticky sessions needed.
- **Model in process**: model is loaded once at startup into each worker. Memory cost ≈ 220 MB per worker × 4 workers per pod ≈ 880 MB / pod. Fits inside our 1 Gi limit.
- **Database**: read-heavy. Primary handles writes; one read replica handles retraining reads.
- **Redis**: single primary with one replica, Standard C1 (1 GB) tier is plenty.
- **Batch endpoint** handles up to 500 tickets per call — used by overnight bulk-categorization jobs that catch up on misrouted historic tickets.

## 5. Failure modes & mitigations

| Failure                                  | Detection                          | Mitigation                                                                 |
|------------------------------------------|------------------------------------|----------------------------------------------------------------------------|
| Pod OOM during high-volume batch         | k8s OOMKilled event → alert         | HPA scales out, batch limit enforced server-side, retries with backoff     |
| Model file corrupt / missing             | Readiness probe fails on `/ready`   | Previous pod versions kept by ACR; rollback via `kubectl rollout undo`     |
| MySQL primary down                       | Probe + Azure metric                | Auto-failover to standby (Azure Flexible Server); writes queued in app     |
| Redis down                               | Connection error in app             | Cache layer degrades open — predictions still served, just no cache hits   |
| Bad model promoted (F1 dropped)          | Drift monitor + canary metric       | New deploy goes through 5% canary first; auto-rollback if F1 < threshold   |
| Sudden vocabulary drift                  | Weekly KS-test on token distribution| Automated retraining job triggered                                         |

## 6. Security

- **TLS everywhere**: ingress, in-cluster mTLS via Linkerd (optional), DB connections use SSL.
- **JWT** with short expiry (60 min) + refresh tokens (24 h).
- **RBAC**:
    - `agent` — can call `/predict`, `/predict/batch`, `/feedback`
    - `admin` — additionally can call `/train`, `/users/*`
    - `system` — service-to-service token used by the CRM webhook
- **Secrets** never live in code or images — pulled from Key Vault by CSI driver at pod start.
- **Container** runs as non-root with read-only root filesystem.
- **Dependency scanning** via GitHub Dependabot + Trivy on every image build.
- **Pre-commit hooks** include `detect-secrets`.

## 7. Data model

```
users
├── id (PK)
├── username (unique)
├── hashed_password
├── role
└── created_at

tickets
├── id (PK)
├── external_id           ← Salesforce/Zendesk ID
├── subject
├── body
├── submitted_by
└── created_at

predictions
├── id (PK)
├── ticket_id (FK → tickets.id)
├── predicted_category
├── confidence
├── model_version
├── routed_to
├── latency_ms
└── created_at

feedback
├── id (PK)
├── ticket_id (FK → tickets.id)
├── correct_category      ← what the agent ultimately tagged it as
├── agent_username
└── created_at
```

The `feedback` table is the gold-label source for weekly retraining — every agent override becomes a training example.
